## 旧实现中的证据缺口

| 入口 | 升级前写入行为 | 对统计的影响 |
| --- | --- | --- |
| `createRequirement` | 网页/Agent 共用，初始属性和负责人同事务保存，但不写创建属性审计 | 需要新增不可变初始事实和覆盖起点 |
| `updateRequirementProperties` | 调用方持行锁；逐字段审计与实际属性同事务，重复或未变化不再写日志 | 适合在最终属性确定后记录里程碑和完整负责人快照 |
| `seed-data.ts` | 直接创建固定说明手册及已发布初值 | 不属于需求/缺陷产出；不能伪装成完成事件 |
| 正式保存、标题保存、关联变更 | 更新正文快照、标题或更新时间，不产生业务流程事实 | 不得用 revision 作者或 updatedAt 代替提测/完成时间 |
| 旧迁移 | `0012` 将单人负责人转为数组，并调整固定手册类型与状态；`0013` 将数组转为关系表 | 迁移不补历史审计，当前关系不能倒推旧事件归属 |

旧日志中的 assigneeId（单个字符串/null）与 assigneeIds（完整数组）需要分别解析。相同 operationId 的状态及负责人变化是一次原子操作，必须采用该操作生效后的名单，不能依赖逐字段审计的 ID 顺序。同一时间多个操作没有可靠次序时标为未知，不用随机 ID 猜先后。

## 已实现的事实与覆盖

- 新建需求/缺陷通过 `initializeMilestoneCoverage` 建立可信初值和按指标覆盖记录，包含完整初始状态、负责人、优先级、来源和创建操作标识。网页和 Agent 使用同一 `createRequirement` 服务；事务失败不留统计事实。说明/待办没有这些产出指标，不建覆盖行。
- 需求第一次进入 testing、需求/缺陷第一次进入 done 产生里程碑；文档/里程碑种类唯一，重复流转、重试和重复审计不重复计数。closed 不等于 done。
- 同时保存事件时间、操作来源/证据和整次变更生效后的负责人 ID 集合。多人各计一次；后续改派、姓名变化或账号停用不改写旧归属。
- 存量记录必须先证明完整初值与状态/负责人链再回填。旧实现没有完整初始事实，因此 `0017_requirement_milestones` 只登记 `missing_initial_state`，不回填里程碑，也不改写旧文档、审计或版本。上线后首次观察到 testing 不能自动成为历史 first_testing；切换时已经 done 也不能补成上线日完成。
- `recordRequirementMilestone` 在属性与审计的同一事务内执行。首次事实按 `(requirementId, kind)` 唯一，负责人快照另有联合主键；重复流转不更新时间或名单。权限及合法流转继续由原属性服务验证。

| 表 | 保存内容 |
| --- | --- |
| `requirement_milestones` | 可证明的首次事件、毫秒精度的数据库时间、来源、关联操作 ID |
| `requirement_milestone_assignees` | 事件生效后完整负责人 ID 集合；不随当前关系和账号名称变化 |
| `requirement_statistic_coverage` | 文档/指标、采集起点、是否完整、可证明的完整范围起点、缺口原因、初始证据及可选观察证据 |

历史完整时 `completeFrom` 为文档创建时间。历史不完整且尚未观察到目标状态时为 null。若迁移时或后续流转明确观察到 testing/done，只能证明历史首次不晚于该观察；保留该次观察时间、来源和名单，以“观察时间 + 1ms”作为之后不可能再有首次事件的完整范围起点。`historyComplete` 和旧缺口不清除，观察当期及更早区间仍未知。再次观察不覆盖第一次证据；没有覆盖行的受控脚本旧记录也按未知处理。

这段“之后完整”仅表示首次事件不可能再次发生，不表示已找回历史时间或负责人。聚合必须按查询区间检查缺口，不能仅凭 `completeFrom` 非空就把当期或全部历史改成完整。缺失历史负责人时也不能仅按当前负责人排除潜在影响。

### 明确授权的手工补录

用户明确指定旧数据的补录时间、事件负责人及范围时，可以将这些值作为一次性人工统计基线；这不代表恢复了真实历史。先备份并在事务中回滚演练，只处理核对过的缺口，不覆盖已存在的里程碑。补录的覆盖证据使用 `type: manual_backfill`，记录 operationId、backfilledAt、assigneeIds 与 reason；来源为 `agent_takeover`。补录后 historyComplete 表示按指定基线已补齐，completeFrom 使用原文档创建时间，实际事件统一落在指定补录时间；旧覆盖证据保留在备份中。

此操作只补统计事件、事件负责人和覆盖记录，不修改当前文档状态、当前负责人、创建时间、正文或版本。补录的事件计入指定日期的产出；后续再次流转仍由里程碑唯一约束去重。普通创建、属性更新和自动迁移继续采用上文的事实规则，不自动执行此类补录。

## 时间和聚合契约

`GET /api/workbench/my-work?period=week|month&date=YYYY-MM-DD` 默认本周，date 为所选周期内任一天。只接受这两个参数；经 `requireAppContext` 取得固定项目及本人 ID，拒绝调用方指定项目或用户。响应 `Cache-Control: no-store`。服务在只读 REPEATABLE READ 事务内取得 asOf、逐日聚合及当前状态，不返回文档或历史负责人明细。

响应包含标准 period（type/startDate/endDate/start/end/observedUntil/current）、timezone、asOf、totals、days、current。endDate/end 均为排他终点。每项数值返回 value（精确总数，number/null）、knownValue（已确认事件数，number/null）、quality（complete/incomplete/future）、completeFrom、reason（null/missing_history/future）。历史缺失时 value 仍为 null，但 knownValue 保留同一范围内已记录的事件，不能因为旧文档的缺口把新文档的可信事件一起隐藏；knownValue 是下界，不是完整总数。完整时两者相等，未来日期两者都为 null；周期 knownValue 等于逐日已确认数之和。

completeFrom 表示已知缺口之后能够保证完整的全局起点：所有缺口都有观察上界时取其最大值，仍有未界定缺口时为 null；本来全历史完整的指标也为 null，结合 quality/reason 区分。查询日期是否完整单独按区间判断，不能仅凭此字段判断。创建类事实完整；历史事件按文档创建时刻至其 completeFrom 之间的潜在缺口判断。缺少覆盖行同样按未知处理，不能仅按当前负责人排除历史潜在归属。其他项目缺口不影响本项目。

周期为 Asia/Shanghai 的自然周（周一开始）或自然月，区间含起点不含终点。服务器返回标准周期与 asOf，拒绝未来周期；当前周期只统计到 asOf。未来日期用 null，已完整覆盖且无事件的日期可为 0。

五项周期指标：本人创建需求、本人首次提测需求、本人完成需求、本人创建缺陷、本人完成缺陷。创建依据 reporterId/createdAt；提测和完成依据事件负责人快照。当前进行中需求只计 doing，当前未完成缺陷排除 done/closed，包含待处理。两项当前数量使用现有负责人和状态，不随周期变化。普通负责人调整只影响当前集合。

当前需求与缺陷分布都按 queued/doing/testing 排列，保留零值。其他未完成状态有当前记录时附在其后，避免遗漏后使缺陷合计与当前数不一致。需求图总和是未完成需求，不等于进行中需求；缺陷图总和等于当前未完成缺陷。

五项汇总和逐日数据使用相同事务快照、过滤和覆盖规则，不新增可越权读取的文档清单。

周期事件与当前状态不要求相等。例如本期新建7条，其中2条已完成、1条已关闭、4条仍未完成，另有之前创建的1条待处理，则当前未完成为5条。曾经首次提测后又完成或退回进行中的文档，仍属于本期提测事件，但不再属于当前测试中状态。
