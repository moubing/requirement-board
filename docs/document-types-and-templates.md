# 文档类型、流程与正文模板

产品统一称为「文档看板」。文档包含需求、缺陷、说明、待办四种类型；类型决定状态流程，四类均支持多人负责，模板只定义正文结构。当前不开放自定义类型、流程设计器或自定义字段。

## 创建与模板

在工作台或列表选择「新建文档」，填写类型、标题和负责人。模板默认「空白模板」，切换类型也重置为空白；选择其他模板时预览其正文。每种类型有一个内置模板：

| 类型 | 模板 | 正文结构 |
| --- | --- | --- |
| 需求 | 标准需求 | 背景与目标、使用场景、详细需求、验收标准 |
| 缺陷 | 缺陷报告 | 问题描述、复现步骤、预期结果、实际结果、环境与附件 |
| 说明 | 通用说明 | 概述、适用范围、详细说明、示例与注意事项 |
| 待办 | 事项待办 | 目标、行动清单、完成标准、补充信息 |

自定义有两个入口：

1. 导航的「模板管理」：新建模板，或复制已有模板，再用现有富文本编辑器定义章节、提示、示例、表格和图片。
2. 文档顶部更多菜单的「另存为模板」：复制打开弹窗时的当前正文（含已同步草稿），不改变状态或生成版本。须先完成图片上传；保存成功关闭并提示，失败保留输入。

模板管理使用灰色页面背景和一张白色圆角大卡片。顶部可按名称/用途搜索，并组合类型、内置/项目来源筛选；搜索为空时展示全部，筛选无结果时显示独立空状态。目录/正文宽屏按43/57分区，工作区≤1100px切为目录/预览单区。目录中模板按双列卡片展示，≤600px切为单列；缩略预览从实际 JSON 提取前三个标题及各自首个段落摘要，并显示剩余章节数、模板用途、类型和来源。选中卡片使用蓝色边框与勾选标记，右侧展示类型、来源、版本、名称、用途和完整正文，内置模板只读说明放在正文下方。

点击模板先预览，有权限时显式进入编辑；未编辑时筛选可自动预览第一条匹配项，编辑中筛选只改变目录，不替换当前输入。目录/预览切换使用 v-show 保留正在编辑的输入与上传。切换模板前须处理未保存内容、未完成或失败的上传；放弃修改重新读取，失败保留本地输入。

模板在固定项目内共享。所有启用项目成员可以创建、使用和复制模板；创建者、项目管理员、系统管理员可以修改项目模板。内置模板只读，复制后定制。保存使用递增版本号；并发覆盖返回 409，页面保留当前输入，需放弃修改并重新载入后再编辑。

模板只管理正文，不增加「严重程度、截止日期、影响版本」等可筛选字段。模板编辑不会修改已创建文档；创建时复制选中模板的最新正文，并重新分配全部块 `diffId`。文档创建后类型固定。

## 状态流程

状态按类型分两套（REQ-26 精简）：

| 类型 | 可用状态（展示顺序） | 初始状态 |
| --- | --- | --- |
| 需求、缺陷、待办 | 待处理 `queued` → 进行中 `doing` → 测试中 `testing` → 已完成 `done`，另有已关闭 `closed` | 待处理 |
| 说明 | 草稿 `draft` → 已发布 `published` → 已归档 `archived` | 草稿 |

同类型内任意两个状态可以直接切换，包括直接完成、关闭和重新打开；箭头只表示常见顺序。服务端只校验目标状态属于该文档类型，否则返回 409 `INVALID_TRANSITION`；新建只能使用该类型的初始状态，网页和 Agent 一致。缺陷不再有「待确认」，无效缺陷直接关闭。业务状态「草稿」只属于说明，与共同草稿、正式版本分别管理，保存版本不自动流转。

详情页状态按钮打开状态选择，列出该类型全部状态并标记当前状态（`aria-current`），选择即保存。请求期间禁用重复操作，成功提示新状态，失败提示原因并保留重试。列表未选类型时状态筛选列出全部启用状态，选了类型只列该类型的状态；按状态分组同样只显示启用状态。

`PATCH /api/requirements/:id` 可携带 `expectedStatusId`：文档当前状态与之不同时返回 409 `STATUS_CONFLICT`，`data.currentStatus` 给出最新状态，不写入任何属性。工作台拖拽和撤销使用它避免覆盖他人修改；详情页属性队列仍按最新选择提交。

状态代码定义在 `shared/documents/workflow.ts`：`DOCUMENT_TYPE_STATES` 为各类型可用状态，`INITIAL_DOCUMENT_STATES` 为初始状态，`DOCUMENT_WORKFLOWS` 是 Agent meta/schema 暴露的契约（`initial`、`states`、`transitions: 'any'`）。旧流程的 9 个状态（待评审、待开发、开发中、待验收、待上线、待确认、待修复、修复中、待验证）只保留名称供历史日志显示；数据库中对应行 `requirement_statuses.active=false`，不出现在 `/api/meta`、Agent meta、筛选和分组中，也不能作为目标状态。当前项目成员沿用原有属性编辑权限；职业角色和负责人身份不增加额外操作权限，也不实现子任务汇总。

## 负责人

需求、缺陷、说明和待办均可分配多位负责人，也可不指定，完整名单最多 100 人。提交的名单中每个人都须为同项目启用成员。列表、搜索、我的文档和成员统计都读取完整名单，修改名单作为一条属性变化记日志。

数据库通过 `requirement_assignees(requirement_id, user_id)` 保存分配关系；联合主键防重，外键保证文档和用户存在。删除文档会级联删除分配关系；仍有分配关系的用户不能直接删除，可先停用或转交。成员归属及启用状态仍由后端写入校验。

接口仅接受 `assigneeIds` 完整名单，空数组清空，不再接受 `assigneeId`。响应提供按用户 ID 排序的 `assigneeIds` 和对应 `assignees`，不返回旧的单人字段。属性写入、分配关系和日志在文档行锁保护下同事务提交，负责人顺序变化不产生日志。历史单人属性日志保持可读。

## 数据与接口

- 保留 `/requirements` 页面、API、`REQ-*` 编号及原表名，以保持已有链接、历史和 Agent 兼容；这些入口现在承载四种文档。
- `requirements.document_type` 保存类型，`requirement_assignees` 保存完整负责人关系；`requirement_statuses.code` 是项目内唯一的稳定状态代码。
- `document_templates` 保存项目、类型、名称、说明、Tiptap JSON、创建者与版本。`GET /api/document-templates` 列出内置和项目模板；POST 新建，`PUT /api/document-templates/:id` 携带 `version` 修改。
- 网页 `POST /api/requirements` 接受 `documentType`、`templateId`、标题和属性；显式 `templateId: null` 为空白，省略时兼容旧请求，使用对应类型内置模板。省略类型默认为需求。初始 v1 包含完整正文，首次共同编辑按需初始化 Yjs。
- 属性 PATCH 及 Agent 操作共用服务端流程和分配校验。Agent 创建接受 `documentType`，自己提供完整正文；`meta/schema` 暴露类型、状态代码和流程。协议版本与能力以目标站点的 `/api/agent/v1/schema` 为准，当前契约见 [Agent 文档](agent-editing.md#格式与图片)。
- 模板图片限于同项目可访问资源或本人的未绑定上传。保存模板时建立项目共享归属，引用写入与 GC 使用共同事务锁。GC 扫描所有模板和全部历史 revision；移除模板图片引用时重新开始宽限期，历史仍引用的图片始终保留。

## 升级与验证

确认目标库后运行 `pnpm db:migrate` 应用完整迁移链，再重启服务。`0013_requirement-assignees` 把原 `assignee_ids` 数组转成关系记录，删除数组列、旧 `assignee_id` 及单人数量约束。应用与迁移须一起升级，旧客户端须改用 `assigneeIds`；不需要重新 seed 或重置数据。

迁移保留文档 ID、编号、正文、revision、Yjs 和编辑收据。旧单人负责人回填成名单，已知状态 ID 保持不变并映射到新代码，补齐状态目录；未知旧状态保留为 `legacy_*`，由后续的状态精简迁移归入新状态。七篇固定使用手册改为「说明 / 已发布」，不改其正文、历史与更新时间。项目使用默认旧名称时改为「文档看板」，自定义名称保持不变。

`20261108045749_simplify_document_states` 迁移存量状态：增加 `requirement_statuses.active`，补齐 8 个启用状态（已存在同代码或同名的不重复创建），停用其余状态并排到最后。文档按类型映射：需求、缺陷、待办的草稿、待评审、待开发、待确认、待修复及未知旧状态进入待处理，开发中、修复中进入进行中，测试中、待验证、待验收、待上线进入测试中，已完成和已关闭不变；说明的已关闭进入已归档，其他非说明状态进入草稿。

每个实际变化写一条 `requirement.property.change` 日志，`source=migration`，同一次迁移共用 operationId。操作者为项目内最早加入的启用管理员，没有时取最早的启用系统管理员。迁移只改状态，不改 ID、编号、正文、版本、负责人和更新时间。迁移日志在属性历史中显示为「系统迁移」，不产生里程碑，也不计入动态和统计。迁移末尾检查每篇文档都处于其类型的可用状态，否则整体回滚。

纯逻辑测试在 `tests/diff/document-workflow.test.ts`，接口测试在 `tests/api/documents.cases.ts`。`pnpm test:browser:documents` 使用本机独立的 `requirement_board_documents_browser_test`、3139 端口及临时上传目录，无头验证四类创建、模板预览与编辑、分配、状态直接切换、失败恢复、筛选及明暗主题和窄屏；结束后关闭临时浏览器与服务并清理文件。
