# REQ-12 长文档输入与切换优化验证

测量日期：2026-10-19。需求为《性能优化2.0：视图切换、侧栏导航与长文档输入》。基线是 `1b3373348167f598d40eff7bce38335dfe754987`，与读取时线上镜像 `requirement-board-app:prod-9-1b3373348167` 一致；候选为该提交上本次工作区改动。两者均使用 npm `@moubing/bing-ui@0.11.2`，没有替换组件库构建产物。

## 实现范围

- 每个编辑事务只导出一次正文 JSON，页面用浅层引用持有不可变正文。指纹、语义比较、Yjs 编码及本机检查点按代次复用，输入时只标记待核对；本机备份仍保留 500 ms 空闲窗口与 1500 ms 最长期限。离页、上传、保存和恢复边界立即核对。
- 已校验文档中的段内字符、标记操作跳过全文块 ID 扫描；结构操作、粘贴、旧文档修复仍完整校验。保留原始 Y.Doc、协作事件、撤销历史和上传副本。
- 阅读锚点缓存候选块并从相邻位置查找，目录缓存标题坐标；几何任务按帧先读后写。隐藏编辑器暂停光标和目录的视觉工作，恢复时取消过期任务。
- 正文和比较器使用独立、稳定尺寸的图层，比较器首次打开才创建，热切换保留 DOM。返回缓存详情时，权限检查之后才允许复用同一正式版本正文，属性、锁与协作状态仍重新核对。
- 离页后，未选中的视图保留实例但暂不参与布局；显式打开后恢复，同一次激活中的热切换保持双方尺寸。避免返回正文时也重新排版整份隐藏的比较结果。
- 连续输入测量暴露了协作确认的锁顺序问题：内部连接即使使用延迟卸载，达到最大合并窗口后仍会等待存储钩子。现在先释放原始编辑的文档锁，再等待连接清理，避免存储钩子等待同一把锁而挂住后续确认和撤销。
- 首次详情的独立请求并发启动，版本列表和关联信息不阻塞正文。没有改变持久化格式、迁移数据库或重建 Yjs 历史。

## 样本与方法

主样本为 REQ-8《ui改版》v6（`rev_B61hjXLGLm6D`）与 v7（`rev_YOa2qiDlsp53`）。v7 含 197 个顶层块、64 个标题、37 张图片、16 张表格，文本节点合计 48,915 字符；37 张原图共 5,288,560 字节。只替换隔离服务中的图片 URL，保留原图字节和正文结构。

`JSON.stringify(contentJson)` 的 SHA-256：

- v6：`cc4daef0ace4d3ad2658c5f8a55d2d242beea2043852b4dc1cbf6b53b4d34ba2`
- v7：`dcfd1dbfe12bbc503711a1c7edca66b30239ff80a22bd6b55c647be8681fd52b`

本机为 Windows 11 专业版（10.0.26200）、Intel Core i5-14600KF、Node 24.18.1、无头 Chromium 148.0.7778.96，视口 1732 × 942、DPR 1，默认动效开启，无网络降速。服务使用生产模式 Nuxt、隔离 PostgreSQL、真实 API/WebSocket 和原图上传，不使用页面或接口桩代替性能测量。性能运行期间不并行构建或其他测试。

每轮热比较切换 20 次，首次打开单列；返回正文 21 次；工作台、文档、模板管理、成员管理各往返 20 次。第一轮另录三段全文滚动：顶部至文末再返回，并在中段快速反向。输入在三文档 LRU 淘汰并重新打开正文后执行，此时比较器未挂载；文首、中段、文末各连续 30 秒英文、数字和标点输入，随后通过真实快捷键撤销，校验正文恢复。CDP 中文组词功能检查与 Windows 搜狗实测分开。

输入同时保留三个口径：`beforeinput → input` 处理时间、两个 rAF 代理值、Trace `EventTiming.duration` 的 Chromium 呈现反馈。未匹配呈现事件单独计数，不以 rAF 补齐。切换和导航计时包含自动化调度、目标 DOM 可用及两个 rAF，不等于目标内容的最终呈现或实体屏幕延迟。

样式、布局和脚本取 CDP 累计 CPU 时间；渲染取同线程 `UpdateLayoutTree / Layout / PrePaint / Paint / Layerize` 区间并集。滚动呈现间隔取 `AnimationFrame::Presentation`；`PipelineReporter` 主报告与 FORKED 派生报告分开统计，不重复计算为独立帧。

## CPU 降速诊断

最终候选在 6 倍限速下只录制一轮：热切换 20 次、每个侧栏入口 20 次往返、三段完整滚动、三处各 30 秒直接输入。未获得相同条件的有效三轮基线，因此不计算优化比例，更不能替代公司电脑实测。

- 直接输入 510 个匹配呈现事件：P50 **153.9**、P95 **206.4**、最大 **269.6 ms**；文首 / 中段 / 文末 P95 为 **199.1 / 213.6 / 199.4 ms**，说明强限速下仍存在明显主线程压力。
- 热比较点击呈现反馈 P95 **524.2 ms**，返回正文 **413.8 ms**。DOM 与两个 rAF 代理的热比较 P95 **1,642.7 ms**，四类返回正文为 **3,142.8–3,747.8 ms**。
- 三段滚动呈现间隔 P95 **99.49 / 58.28 / 74.92 ms**，主报告丢帧 **4,528 / 2,780 / 3,528**。这些诊断结果未达到需求的低性能体验目标。
- 纯切换/滚动及连续输入撤销后，服务器全文签名均恢复。随后缓存安全检查在接收远端增量时超过默认 5 秒等待；原失败保留在该轮 `results.json`，不能把这一轮标为完整通过。
- 后续用新建的同样本长文档独立复查，6 倍限速、每项功能等待上限 30 秒，远端增量、双重恢复门禁、辅助请求失败、AI 锁/代次、403 淘汰和账号隔离全部通过，整组用时 35.1 秒。这验证功能可以完成，未复现原轮次的长时间编辑历史，也不证明原 5 秒超时已解决。

## 验收状态与产物

本次沿用需求已有的建议预算，没有按测量结果放宽。代码实现和本地功能回归已完成，**整个 REQ-12 尚未达到全部性能验收条件**：

- 普通机、原长文档、三轮直接输入的已匹配呈现指标满足预算；热切换点击反馈满足首次反馈预算。
- 热切换最终内容呈现、各侧栏路径最终内容呈现仍需进一步对齐；已有代理值不能判定全部达标，部分方向没有改善。首次比较也未证明提速。
- 6 倍限速诊断仍明显偏慢；原长时间操作后的缓存安全 5 秒超时保留为未解决记录。新文档功能复查不覆盖该长历史条件。
- 中文确认目前只有补充样本的一轮 CDP 数据，缺少原样本优化前后三轮和真实搜狗数据；短文档文首有一次组 P95 超预算。
- 公司 Xeon 电脑的两类输入、切换、导航和滚动矩阵尚未实测，不以本机降速替代。
